# 设计取舍记录（ADR 摘要）

每个选择都记录了**替代方案**和**放弃理由**——读代码时最容易问"为什么不那样做"，答案在这里。

## 1. 为什么做成 MCP 服务器，而不是继续写脚本

- 直接脚本：`python art.py "初音未来 泳装"`，简单，但能力被锁在"会跑命令行的人"手里。
- MCP 服务器：能力被声明成**带 schema 的工具**，任何支持 MCP 的宿主（桌面 Agent、编辑器、自研客户端）都能发现并调用，调用参数由宿主校验。

代价：多一层协议与进程管理（stdio 生命周期、HTTP 端口占用）。收益：能力可复用、可被审计（工具名、参数、返回都在协议层可见）。

## 2. 为什么 tag 编译是"规则表"而不是再调一次大模型

- 让模型直接产出 booru tag：灵活，但对齐差，同一句话两次可能给出不同 tag，还会凭空造 tag（站点搜不到）。
- 规则表 + 优先级替换：确定、可测（26 条 golden case 全离线）、零 token 成本；未知词作为 `unknown_words` 原样返回，让宿主决定要不要再问模型。

代价：中文口语覆盖靠人工词表扩充。收益：可解释、可回归——改了词表跑一遍评测就知道有没有退步。

## 3. 为什么先做"松弛阶梯"再报错

图站对多 tag 交集很严格：`cherry_blossoms flower_field scenery` 可能真的是 0 条，但 `cherry_blossoms` 有几十万条。
一次查询失败就返回"没找到"，用户会认为工具坏了。所以按 `全条件 → 去掉方向约束 → 逐个减 tag` 逐级重试，并在返回里标记 `relaxed` / `attempt`，让宿主知道结果是不是打了折扣。实测把 6 个用例的联网成功率从 3/6 提升到 6/6。

代价：最坏情况多几次 HTTP 请求。收益：用户侧"能出图"的概率显著提高，且降级是**显式**的。

## 4. 为什么评分用"短评分别名 + 安全白名单"

不同图站对分级的拼写不一致：Gelbooru 系返回 `s`/`q`/`e`，另一些返回 `safe`/`questionable`/`explicit`。
只认 `safe` 会把合法结果全部丢掉（这个 bug 真实发生过：12 条结果被过滤成 0 条）。所以先归一化再判断，且**只放行 safe**——宁可少给图，也不给不确定的内容。

## 5. 为什么 SQLite 用 `mode=ro` 打开

记忆库是另一个进程在写的（带 WAL）。工具只需要读：用 `file:...?mode=ro` 打开，物理上排除写坏的可能；同时避免长期持有写锁影响主程序。查不到就报 `FileNotFoundError`，不偷偷建库。

## 6. 为什么竞技场查询要经过本机浏览器服务

上游接口有风控（匿名请求返回 103/601）。在本机跑一个有登录态的真实浏览器，由页面自己发请求、工具侧只截取结果，等价于"人手动查"。
所以工具侧只依赖一个本地 HTTP 契约（`POST /search`），不携带任何凭证——凭证留在浏览器 profile 里，不进代码、不进仓库。

## 7. 为什么健康检查用 TCP 连接而不是 HTTP 探活

五个本地服务协议各不相同（WebSocket、HTTP、私有 TCP）。TCP connect 是唯一对它们都成立、又足够快的判据（0.6 秒超时）。
它证明"端口在监听"，不证明"服务健康"——所以 README 里明确写这是 liveness，不是 readiness。

## 8. 为什么没有引入向量库

26 条 golden case、几十到几千条记忆的规模下，token 重叠打分（含重要性先验）足够，且零依赖、可解释、可在 CI 里跑。
规模上到十万级再考虑 embedding；届时替换点是 `memory.score()` 和 `_tokens()` 两个函数，不影响协议层。
